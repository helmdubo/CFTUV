# Карточка: почему центральный патч считается минутами

**Ветка:** `claude/arrangement-counters-and-scaling`
**База:** `claude/project-critical-analysis-t8qz7s`, коммит `98c3a09`
**Пушить:** только в свою ветку, `git push -u origin claude/arrangement-counters-and-scaling`
**Цель по масштабу:** до 2000 выделенных рёбер. Сегодня 5 рёбер — 12.4 с.

---

## Что уже измерено (это факты, не гипотезы — не перепроверять заново)

**Полевой прогон, `building.002`, 5 рёбер, 6 доменов:** 12.4 с, из них 11.8 с —
один центральный патч `bf6`. Остальные пять — по ~130 мс. Отношение времён при
границе больше в 4–5 раз: 60× / 268× / 60× по стадиям, то есть показатель
степени где-то 3.5–4.

**Раздувания коэффициентов нет.** Разрядность числителя и знаменателя на
1 305 764 реальных значениях: медиана 3 бита, 99-й перцентиль 19, максимум 29.
Шире 64 бит — ноль значений. Отказ от точных конструкций в пользу float ничего
не выиграл бы на этой оси: числа и так помещаются в машинное слово.

**Символьный путь практически не используется.** 1.26M вызовов `exact_sign`,
из них в интервальный фильтр уходит 642, в полный символьный — 0.

**Машина предположений SymPy больше не будится** (коммит `98c3a09`): было
885 625 вызовов `deduce_all_facts`, ~50% self-time; стало 240 на весь прогон.
`test_session_d_resolved_coverage.py`: 32.4 с → 10.5 с.

**Синтетический стенд не воспроизводит полевую степень.**
`tools/benchmark_arrangement_scaling.py` даёт O(n^1.2–1.6) по обеим осям
(и по числу сегментов границы, и по числу вкладов). Broadphase — не перебор
всех пар: 61 пара на 40 сегментов. Значит, полевая степень берётся **не** из
самого arrangement на этих размерах, и стенд её не покажет.

**Профиль после `98c3a09` плоский**: ни одной функции больше ~10%.

## Отсюда следует задача

Гадать больше не о чем: нужны **полевые счётчики того самого патча `bf6`**.
Они уже считаются ядром и умирают внутри него, не доходя до хоста.

`ArrangementBuildCountersV1` (`kernel/src/cftuv_envelope/reference/arrangement.py:97`)
→ поля `*_count` на `ArrangementUnionV2` → **дальше некуда**:
`RawCoverageResultV1` их не несёт, хост про них не знает.

### Шаг 1 — довести счётчики до хоста

Носитель — `ReferenceEvaluationResultV1` (`reference/contracts.py:297`), **не**
`RawCoverageResultV1`.

Это принципиально: `raw_coverage_semantic_digest` считается по
`RawCoverageResultV1` целиком, кроме поля `semantic_digest`. Любое новое поле
там — включая `diagnostics` — меняет дайджест всей семантики.
`ReferenceEvaluationResultV1` в дайджест не входит, проверено по
`reference/digest.py`.

Дальше: хост читает счётчики в `cftuv/envelope_request_export.py` рядом с
`kernel.evaluate_reference_raw_coverage` (строка ~2633) и кладёт их через
`builder.set_counter(name, value, patch_domain_id)` — API уже есть в
`cftuv/envelope_debug_profile.py:189`, и оно уже принимает `patch_domain_id`,
то есть разрез «по патчам» получается бесплатно.

Минимум, который нужно видеть на каждый домен:
`input_segments`, `all_possible_pairs`, `broadphase_candidate_pairs`,
`narrowphase_tests`, `actual_intersections`, `atomic_edges`.

Ворота шага: дайджесты не изменились (весь набор ядра и хоста зелёный —
626 и 809), и в полевом выводе видно строку счётчиков по `bf6`.

### Шаг 2 — прочитать, что вышло, и только потом чинить

Три исхода, три разных лечения. Заранее выбирать нельзя.

| Что покажут счётчики | Диагноз | Лечение |
|---|---|---|
| `broadphase_candidate_pairs` ≈ `all_possible_pairs` | AABB-фильтр на этом патче не фильтрует (полосы огибающих перекрывают всё) | sweep-line или сетка вместо перебора пар |
| `atomic_edges` ≫ `actual_intersections` | взрыв идёт от разбиения, а не от пересечений | разбирать, что порождает атомарные рёбра |
| счётчики скромные, время большое | цена в другом месте — point location или `_point_in_region` | шаг 4 ROADMAP: плавающий фильтр + trapezoidal map |

### Шаг 3 — зафиксировать результат исполняемым порогом

Не отчётом. Тест, который падает, если счётчики поехали:
предел на `broadphase_candidate_pairs / actual_intersections` на портируемой
фикстуре, снятой с реального патча.

## Чего делать НЕ надо

- **Не переходить на float-конструкции ради скорости.** Владелец согласен на
  дрейф вершин декалей, но замер выше показывает, что на этой оси выигрыша нет:
  раздувания коэффициентов не существует. Дайджест — семантическая
  идентичность, и менять его основание ради нуля выигрыша нельзя.
- **Не менять `ExactScalar` на `Fraction`.** Проверено: `Fraction` не быстрее
  `sympy.Rational` на арифметике (2.9 мкс против 2.1). Вся разница, которая
  казалась разницей представления, была в машине предположений, и она уже снята.
- **Не оптимизировать по микробенчмарку на одном значении.** Ровно так был
  списан верный профиль и потерян месяц (см. ROADMAP, «Важно про
  профилирование»). Мерить на свежих значениях.
- **Не трогать `MITER`/`BEVEL`** — в envelope их нет, их заменяет динамический
  профиль от reflex angle.

## Как воспроизвести замеры

```bash
PYTHONPATH=kernel/src python3 -m pytest -q kernel/tests -p no:cacheprovider
python3 -m pytest -q tests -p no:cacheprovider
PYTHONPATH=kernel/src python3 tools/benchmark_arrangement_scaling.py --contributions 4
python3 tools/blender_check_install.py --fingerprint
```

Полевой прогон делает владелец: `E:\testscene.blend`, меш `building.002`,
Build Envelope Debug. Отпечаток установленной копии обязан совпасть с
`--fingerprint` — иначе в Blender лежит другая ветка, и это уже случалось.
