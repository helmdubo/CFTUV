## 0. Repo-вопрос: новый проект или мутация старого

**Рекомендация: НЕ новый repo. Greenfield на уровне ПАКЕТА внутри
текущего repo + механическая стена импортов.**

Почему полный rewrite («CFTUV+, зная лишь идеи») опаснее:
1. **Уроки живут не в идеях, а в исполняемых артефактах.** Эта
   ветка доказала: записанные правила перечитываются неверно
   («нашлёпки», «BEVEL=MITER» — оба раза буква директивы победила
   смысл). Реально защищают: fixture-сюита RF*, полевой harness
   шести объектов, differential-паттерн S0, гейт 0d.0,
   import-ban тесты, инварианты как тесты. Новый repo стартует
   БЕЗ них; перенос = недели работы, а перенесённое без старого
   кода не прогоняется.
2. **Analysis-слой один на два потребителя.** PatchGraph/pChains/
   классификация патчей питают и UV-solve, и декали. Новый repo
   либо дублирует analysis (болезнь «двух представлений» в
   масштабе репозитория), либо зависит от старого — и тогда это
   не новый проект, а пакет, оформленный дорого.
3. **TRANCHE S уже сделал главную работу выкорчёвывания:** архив
   S0 (-8k строк), контракты S1/S2a (surface_ir, typed
   boundaries), CornerModel, witness-оракул, SessionController.
   То, что стоит сохранить, УЖЕ отделено контрактами; то, что
   модель C заменяет, — по сути один монолит decal_voronoi.
4. Страх «проползания старых идей» решается механикой, а не
   границей репозитория: **import-ban тест** (у нас уже есть
   прецедент из S0: «shared geometry не импортирует архивный
   backend»). Граница репозитория НЕ мешает агенту скопировать
   старый паттерн; тест на импорт — мешает каждый коммит.

Схема (strangler-fig):
```
cftuv/decal_envelope/        # НОВЫЙ пакет, greenfield
    может импортировать ТОЛЬКО:
      surface_ir, model-контракты, corner_model,
      distance_witness, GeometryBatch, session-API
    ЗАПРЕЩЕНО импортировать: decal_voronoi, decals(legacy-части)
    (запрет — исполняемый тест, не соглашение)
cftuv/decal_voronoi.py       # остаётся: базлайн/оракул/production
                             # до полевого доказательства E6,
                             # затем архив по S0-паттерну
```
Если после миграции пользователь захочет переименовать проект в
CFTUV+ — это будет косметика поверх чистого дерева, а не способ
достижения чистоты.

## 1. Роли вместо подклассов (ответ на вопрос о pChain/Patch)

**Подклассы pChain и Patch НЕ вводить.** Уроки канона (RR8a:
owner — не свойство rail, а атрибуция его кусков) и поля: одна и
та же физическая цепочка — spine для одной декали, boundary для
соседней, контур для третьей. Роль — свойство ИСПОЛЬЗОВАНИЯ, не
объекта. Подклассы заморозили бы роль в identity и вернули бы
болезнь двух представлений при смене роли.

Вместо этого — типизированные ВИДЫ (views) в новом IR:
```python
class ChainRole(Enum): SPINE; BOUNDARY; CONTOUR; BARRIER
@dataclass(frozen=True)
class ChainUse:            # атрибуция, не подкласс
    chain_id: ChainId
    role: ChainRole
    side: BandSide | None
    interval: StationInterval

class DomainKind(Enum): PLANAR; DEVELOPABLE; CURVED
@dataclass(frozen=True)
class PatchDomain:         # вид патча для envelope-бэкенда
    patch_id: PatchId
    kind: DomainKind       # существующая классификация, RP-предикат
    frame: PlanarFrame | None   # точная плоскость для PLANAR
```
Патчи получают обёртку-домен (PLANAR — точная плоскость; CURVED —
territorija R3/SurfaceWavefront), но НЕ иерархию наследования.
Ленточные (ribbon) патчи — тот же DomainKind-механизм.

## 2. Целевая архитектура (фиксация модели C)

```
AnalysisBundle (есть)
    ↓
DecalSkeletonIR            # скелет ЗАДАН пользователем:
    ChainUse[] (роли)      # никакого вычисления medial axis
    Terminal[] / Sector[] / Barrier[]
    ↓
EnvelopePrimitiveIR        # МАТЕРИЯ = union примитивов
    StripEnvelope          # 2 supporting lines, аффинно по alpha
    CornerEnvelope         # семантический контур V/P1/P2 (+ ROUND_k позже)
    CapEnvelope            # торцы (RR9-иерархия наследуется)
    JunctionEnvelope       # T/X: ОДИН семантический регион
    ↓
CoverageArrangement        # exact union ВНУТРИ компонента,
                           # клип доменом; силуэт = ТОЛЬКО граница union
    ↓
InterComponentCompetition  # RC1-RC3 freeze МЕЖДУ компонентами
                           # (двухскоуповое правило — см. заметку)
    ↓
OwnershipPartition         # внутри покрытия: станции/(s,r)/UV/
                           # provenance; НЕ имеет права трогать силуэт
                           # (структурный ассерт)
    ↓
EventLedger                # alpha-интервалы: события collapse/meet/
                           # saturation; drag между событиями
                           # переиспользует комбинаторику (I1)
    ↓
Semantic Coalescing → GeometryBatch (есть) → адаптеры (есть)
```

Инварианты I1-I9 действуют без изменений; новые структурные
ассерты: (a) внутрикомпонентный ownership-раздел не касается
силуэта; (b) число runtime-граней не входит в определение
примитива (тесселяция downstream).

## 3. Фазы

### E0 — Контракты и стена (малый срез)
Пакет, import-ban тест, все DTO выше (frozen, enums, tagged),
curvature-readiness чеклист на каждый контракт. БЕЗ геометрии.
Выход: контракты + ревью двух ревьюверов.

### E1 — StripEnvelope + exact union (research)
Аналитические стрипы, union в arrangement, клип доменом; сверка
witness-оракулом (ширина/владелец/утечки). Фикстуры: изолированный
сегмент, прямая цепочка, два перекрывающихся стрипа одного
компонента (силуэт без внутренних следов). Парабола невозможна ПО
ПОСТРОЕНИЮ — проверить негативом.

### E2 — CornerEnvelope + CapEnvelope (research)
MITER/BEVEL как профили одного примитива; приёмка по
семантическому контуру (V/P1/P2; планарный оракул — одна грань из
трёх вершин); CGAL/pySVCGAL-оракул на замкнутых поддоменах;
linear-axis-сидинг — ТОЛЬКО если доказуемо порождает продуктовый
контур. Капы: RR9-иерархия (pChain -> fold/border -> перпендикуляр)
как параметры CapEnvelope. ROUND_k — контракт заложить, реализацию
отложить.
**Гейт E2:** данные E1-E2 против PatchVoronoi и kinetic-модели B
(та самая трёхмодельная сверка) -> решение двух ревьюверов +
пользователя о продолжении productization.

### E3 — OwnershipPartition
Станции/(s,r)/UV/provenance внутри покрытия; witness-конкуренция
(first/second) как диагностика; перенос RM6a-уроков (общие ключи,
один источник геометрии интерфейсов). Ассерт «раздел не трогает
силуэт» — с E3 навсегда.

### E4 — EventLedger + drag
Компиляция alpha-интервалов (события: collapse ребра union,
встреча примитивов, насыщение, край домена); drag между событиями
не перестраивает arrangement; CapacityPolicy получает доказанные
высоты. Перф-цель: drag-кадр без exact-пересборки.

### E5 — Межкомпонентная конкуренция
RC1-RC3 station-freeze на границах union-покрытий компонентов;
RF7 (ползущая сетка) и RF17 (нити) переезжают как есть.

### E6 — Полевое озеленение (differential)
S0-паттерн: там, где семантика совпадает с PatchVoronoi —
пиксельные/digest сверки; где отличие НАМЕРЕННОЕ (исчезнувшие
параболы/fan) — intentional-diff список; полный полевой набор,
гейт 0d.0, личная приёмка пользователя.

### E7 — Переключение маршрутизации и архив PatchVoronoi
Capability cut -> физический архив по S0-паттерну (ветка + тег +
product contract уже в GeometryBatch-семантике).

R3 (кривизна): отдельная нога — SurfaceWavefront под ОБЩИМ
EventLedger/GeometryBatch-контрактом; порядок E-фаз против R3 —
решение пользователя на гейте E2 (данные покажут стоимость).

## 4. Риски и анти-костыльные ограждения

| # | Риск | Ограждение |
|---|---|---|
| 1 | Робастность exact union (касания, вырожденные перекрытия) | точная арифметика в arrangement; CGAL-оракул на каждом шаге разработки; вырождение -> именованный fail, не epsilon |
| 2 | Перф: arrangement на каждый drag-кадр | EventLedger (E4): комбинаторика стабильна между событиями; drag = параметрическое обновление координат |
| 3 | UV-швы внутри материи на стыках примитивов | один источник: интерфейс примитивов считается один раз, оба читают (RM6a-дисциплина); сверка witness-оракулом |
| 4 | Смешение скоупов (меж/внутрикомпонентный) | структурный ассерт силуэта; фикстура-негатив |
| 5 | Тихий фолбэк в PatchVoronoi на трудном кейсе | ЗАПРЕЩЁН (урок LEGACY-CUT): именованный fail; PatchVoronoi — только оракул |
| 6 | JunctionEnvelope — наименее изученный примитив | один семантический регион; нет чистой формы -> дизайн-стоп, не fan |
| 7 | Расползание на кривизну раньше времени | E-фазы strictly PLANAR domain; кривизна — R3-нога |
| 8 | Двойное сопровождение бэкендов в миграции | maintenance mode PatchVoronoi уже объявлен; E6 ограничен по времени решением гейта |
| 9 | Проползание старых идей | import-ban тест; каталог болезней Б1-Б7 в приёмке ревью каждого E-среза |

**Потенциальные костыли, которых можно избежать заранее** (по
опыту саги): «нашлёпка» поверх union вместо правки примитива;
«подрежем чуть-чуть» на стыке скоупов; повторное вычисление
интерфейса двумя примитивами; политика join вне CornerEnvelope;
подбор k/epsilon под фикстуру. Все пять — уже именованные
запреты в каноне/заметке; в приёмку каждого среза включается
чек-лист по ним.

## 5. Сильные стороны модели C (краткая сводка)
- Силуэт корректен ПО ПОСТРОЕНИЮ (парабол/fan не существует).
- Минимальная тесселяция = цель пользователя «оптимальная сетка».
- Разделение coverage/ownership убивает класс болезней RC5-*.
- Переиспользование выстраданного: CornerModel, GeometryBatch,
  witness, arrangement-инфраструктура, полевой harness.
- Join'ы = профили одного примитива (ROUND_k бесплатно позже).
- EventLedger формализует I1 и даёт доказанное насыщение.
