# Rail-оракул: русла течения декалей (TRANCHE R)

Статус: **APPROVED — утверждено пользователем; документ является каноном.**
Происхождение: полевые тесты 3-4 (SN-принцип, «берега русла»),
требование пользователя: только детерминированные топологические
правила, никаких эвристик и подбора чисел.

Runtime status: **R0 + R1 IMPLEMENTED** (`ed20953`, `572198e`,
`21d9d6e`) — RR1-RR7 компилируются в immutable rail-plan, а строгий
`RAIL_PLANAR` материализует принятые PLANAR-компоненты по RM1-RM3,
RM5/RM5a и ограниченному R1-контракту RM6. Shared semantic keys
получают единственный канонический offset-lift без spatial post-weld.
R2-R4 ещё не подключены; конкурирующие, криволинейные и неподдержанные
компоненты остаются на production Patch/chart пути. Автоматическая и
локальная Blender-проверка R1 зелёные; финальная полевая приёмка §0d
ожидает подготовленную пользователем сцену.

Роли слоёв (пивот архитектуры):
- **Rail-домен — единственный источник ГЕОМЕТРИИ ленты.**
- **Конкуренция (Voronoi-роль) — в станционной метрике русел:**
  кто владеет спорной зоной, где freeze.
- **Chart/UV — строится ИЗ rail-домена** (один источник, много
  читателей — урок GL закладывается с первого дня).
- Числа в системе — только СЕМАНТИКА (ширина, квант B0, бюджет
  G3). Все ВЫБОРЫ ПОВЕДЕНИЯ — топология, provenance, разметка.

---

## 1. Определения

- **Spine (хребет)** — выделенная цепочка seam-рёбер (pChain),
  источник ленты.
- **Rail (берег)** — путь рёбер меша, по которому фронтир течёт
  от spine в глубину поверхности.
- **Rail-станция** — вершина на rail с накопленной длиной рёбер
  от spine (compile-факт).
- **Русло (channel)** — полоса граней между двумя соседними
  rails.
- **Плотина (dam)** — детерминированная остановка rail на
  топологической неоднозначности.
- **Rail-mark** — явная пометка ребра артистом («мост» через
  неоднозначность).
- **Полюс** — вершина, в которой сходятся несколько rails
  (N-fan без единственного продолжения).

## 2. Правила трассировки RR (только топология)

**RR1 — Старт.** На каждой вершине spine, на каждой стороне,
rail стартует из ЕДИНСТВЕННОГО ребра, общего для двух граней
этой стороны, инцидентных spine-рёбрам вершины (регулярный
quad-стык). Нет единственности (fan из 1 или >2 граней, missing
quad) — плотина на старте либо rail-mark.

**RR1a — Секторные старты на multi-spine/boundary вершине
(директива по третьему стопу R1.1, building vertex 231).**
На spine-вершине веер граней band-стороны РАЗДЕЛЯЕТСЯ
делимитерами — spine-рёбрами и boundary-rails (RR8) — на СЕКТОРА
(максимальные пробеги веера между делимитерами). Правило RR1 —
частный случай для прямой вершины (один сектор через оба
spine-ребра). Обобщение, по сектору:
- ровно ОДНО внутреннее ребро веера -> обычный rail стартует из
  него (стандартная трассировка RR2 дальше; это полноценный route
  в routing IR со своими станциями);
- НОЛЬ внутренних рёбер -> rail не нужен: единственная грань
  сектора — угловое русло, ограниченное делимитерами напрямую
  (вырожденный RM7-клин);
- >= 2 внутренних рёбер -> плотина на старте сектора / rail-mark
  (RR3-семантика), далее RM5a.
Building v231: сектор стены A = (77, ребро 417, 167) -> rail по
417; сектор стены B = (149, ребро 472, 300) -> rail по 472; грани
77/149 присвоены, start-DAM и пустой virtual cap не возникают.
Уточнение RM7: с секторными rails «угловое русло» — ОБЫЧНОЕ русло
между секторным rail и boundary-rail;специальный случай RM7
остаётся только для сектора без внутренних рёбер.
Инварианты против второго представления boundary (ответ на
вопрос 3): (i) рёбра boundary-цепочки принадлежат ИСКЛЮЧИТЕЛЬНО
boundary-route — никакой другой route не может их содержать;
(ii) станции boundary-route считаются один раз (RR8a); секторные
rails имеют СВОИ станции по своим рёбрам; (iii) сварка углового
русла с boundary — по общим source-face/vertex ключам RM1, без
переноса станций. Вариант «bridge pieces назад по вееру внутри
boundary-route» ОТКЛОНЁН: контрабанда структуры русла в 1D-rail,
второсортное представление того, что является руслами и rails.

**RR1b — Классификация секторов по делимитерам (директива по
четвёртому стопу R1.1, building vertex 153; признание: третья
ветвь RR1a была неполна — не различала тип делимитеров).**
- **Сектор spine-spine** (оба делимитера — spine-рёбра):
  1 внутреннее ребро -> обычный rail (классический RR1);
  0 или >= 2 внутренних рёбер -> УГЛОВОЙ СЕКТОР -> обслуживается
  corner-путём RM6 (в R1 — стабильная A10-геометрия in-plane
  поворота), который и ЗАКРЫВАЕТ оба смежных русла. Dam-route НЕ
  создаётся, RM5a НЕ вызывается — cap не нужен, закрытие даёт
  угловая геометрия. Building v153 — ровно этот случай: выход
  конструктивного перпендикуляра за owner-face при r>0 — симптом
  того, что сектор угловой, а не rail-ambiguity. Численного
  критерия «угол против прямой» НЕ вводится: классификация
  только по числу внутренних рёбер и типу делимитеров.
- **Сектор spine+boundary / spine+border**: прежние правила RR1a
  (1 -> rail; 0 -> вырожденный RM7; >= 2 -> плотина + RM5a).

**RM5a-деградация (структурный cap).** Если для ЛЕГАЛЬНОГО
RM5a-случая (сектор spine+boundary/border) конструктивный
перпендикуляр покидает owner-face уже при r>0 (точный
геометрический факт, без допусков), cap следует СТРУКТУРНОЙ
границе: первому внутреннему ребру сектора, смежному с гранью
spine-ребра данной стороны — топологично, единственно,
surface-native (лента честно заканчивается по ребру меша).
Запрет «выбора направления» не нарушен: ребро — факт топологии,
не подбор. Taper к нулю по-прежнему запрещён.

**RR2 — Продолжение.** Из вершины rail продолжается в ребро, НЕ
делящее грань с входящим ребром (edge-loop правило), и ТОЛЬКО
если такое ребро единственно (регулярная валентность-4 вершина).

**RR3 — Плотина.** Ноль или >= 2 кандидатов продолжения —
детерминированный стоп: станция-плотина. Событие counted и
видно в подсветке русла. Запрещены: угловые критерии, выбор по
индексам/длинам, любой численный tie-break.

**RR4 — Разметка-мост.** Помеченное артистом ребро (rail-mark),
инцидентное текущей вершине, продолжает rail через
неоднозначность. Разметка + топология = полная спецификация
течения; больше НИЧТО на выбор не влияет.

**RR5 — Границы (терминация).** Rail завершается при:
(a) достижении вершины любого spine (своего или чужого) —
граница: поток НЕ пересекает spine, транс-срез ленты скользит
вдоль него (полевой кейс стены);
(b) полюсе (N-fan без единственного продолжения);
(c) исчерпании alpha_budget по накопленной длине (параметр
ширины — семантика, не эвристика);
(d) плотине (RR3).
Граница (a) сильнее разметки: rail-mark, ведущий в spine,
терминируется на spine (негативная фикстура RF8).

**RR6 — Слияние rails.** Два rail'а, пришедшие в одну вершину, —
merge-станция: русло-клин между ними закрывается, дальше течёт
один rail (по RR2 от вершины слияния). Детерминированное
топологическое событие, counted.

**RR8 — Принудительные boundary-rails (полевая поправка, тест 5).**
Seam-ребро (любой pChain, выбранный или нет), инцидентное
spine-вершине и НЕ принадлежащее самому spine, — ПРИНУДИТЕЛЬНЫЙ
boundary-rail с ВЫСШИМ приоритетом (над RR1/RR2): фронтир
скользит вдоль него, он одновременно граница и направляющая
(«берег» в буквальном смысле — полевой скрин: синие стрелки из
конечной вершины spine). Продолжение boundary-rail — вдоль его
СОБСТВЕННОЙ seam-цепочки (топологическое продолжение цепочки),
не quad-loop. Терминация: alpha_budget по накопленной длине,
конец цепочки (дальше — плотина/CAP), встреча другого spine.
Уточнение RR5(a): «терминация на вершине spine» относится к
rail, встречающему spine ПОПЕРЁК; seam-ребро, идущее В
направлении расширения ленты, — не терминатор, а сам rail.

**RM7 — Угол у конца spine (стык с boundary-rail): простой
вариант.** Угловое русло (веер граней между последним обычным
rail и boundary-rail) материализуется по граням источника как
обычное русло, БЕЗ диагонального митиринга. Митиринг — вопрос
UV-слоя (R4) и/или bands-среза после R3; решение ревьювера по
текстурированным полевым скринам, не заранее.

**RR8a — Ownership boundary-rail на fold'е (директива по второму
стопу R1.1, building).** Boundary-rail — ОДНА топологическая
1D-сущность на seam-цепочку: её станции считаются ОДИН раз
(«один источник, много читателей»). Owner — НЕ свойство rail, а
атрибуция его PIECES относительно каждого смежного
face-sector/русла: для материализации русла на стороне X
участвуют только куски rail, граничащие с гранями стороны X;
дальняя сторона fold'а НЕ участвует и НЕ МОЖЕТ дисквалифицировать
route (building: pChain 476 на ребре стен 79|149 под 90 град. —
легальный общий берег обоих секторов; pChain 598 с key-гранями
двух ориентаций — берег ДВУХ русел одной декали, по куску на
сектор). Residual-запрет `RAIL_GEOMETRY_CURVED_OWNER_UNSUPPORTED`
(R1-объём) применяется только там, где выходит за R1 сама
МАТЕРИАЛИЗУЕМАЯ сторона route (его собственные support-грани);
наличие не-копланарной грани по ту сторону rail — никогда не
причина отказа. Вариант «route на каждый face-sector» ОТКЛОНЁН:
два route на одну физическую кривую = «два представления одного
идеального объекта» — класс болезни, истреблённый в проекте
(двойные квантизации станций разорвали бы сварку угла); общность
станций достигается единственностью route, а не синхронизацией
дубликатов.

**RR7 — Компайл-статичность (S1).** Трассировка и станции
вычисляются на compile до alpha_budget и НЕ зависят от текущей
ширины drag. Drag меняет только материализованный extent вдоль
уже трассированных русел. `Construct()`/трассировка в кадре
запрещены.

**RV1 — Область валидации source-геометрии (директива по стопу
R1.1, полевой building).** Валидация следует материализации:
fail-fast применяется РОВНО к footprint скомпилированного
rail-плана — support-грани русел (обычных, виртуальных RM5a и
угловых RM7) до alpha_budget плюс грани, участвующие в
RR-решениях у spine-вершин. Footprint — конструктивный
compile-факт (грани, которых лента коснётся), не «выбранные
patches» (слишком грубо и косвенно) и не весь PatchGraph.
Геометрия ВНЕ footprint не валидируется и НЕ МОЖЕТ провалить
компиляцию (counted-диагностика допустима, отказ — нет): игровой
ассет всегда содержит грязную грань где-то вдали, и инструмент не
должен быть её заложником. Внутри footprint отказ обязан называть
конкретную грань и причину.

**RV2 — SOURCE_TRIANGLE_DEGENERATE только для истинно вырожденных
граней.** Коллинеарная тройка в fan-триангуляции ВАЛИДНОЙ грани
(building face 277: 6-gon, area 36.65) — артефакт выбора pivot
триангулятора, не дефект меша: коллинеарные вершины на прямом
ребре — штатная топология игровых ассетов. Обрабатывается
робастной триангуляцией (пропуск нулевых fan-треугольников /
ear-clip), НЕ отказом. Отказ — только для истинно вырожденных
граней (нулевая площадь / все вершины коллинеарны), с именем
грани.

## 3. Правила материализации RM (surface-native)

**RM1 — Геометрия по граням source-меша.** Лента эмитируется по
руслам: каждый quad лежит в плоскости своей source-грани ПО
ПОСТРОЕНИЮ; перегибы наследуют source-рёбра. Поперечные пары
вершин (верх_i/низ_i) существуют автоматически — отдельный
imprint-шаг для SEGMENT-интерьеров отмирает (поглощает G1.2).

**RM2 — Координаты rail-домена (поправка по стопу R1;
первоначальная редакция содержала инверсию — признано).**
Внутренние координаты НЕЙТРАЛЬНЫ и именуются (s, r): s — станции
вдоль spine (существующая механика), r — накопленная длина рёбер
rail поперёк (измеренный факт). Публичный UV-контракт НЕ
переопределяется: bands-оракул и материализатор сохраняют
U — поперёк (u_frac * alpha), V — вдоль/phase. Отображение
(s, r) -> (U, V) выполняется ОДИН раз в R4 по существующему
контракту; слои R1-R3 оперируют только (s, r).

**RM3 — Сужение/расширение русла.** Rails сходятся/расходятся —
геометрия следует руслу как есть; компенсация — в UV-слое
(chart из rail-домена), не в геометрии.

**RM4 — Слияние на эмиссии (convex-сплиты).** Критерий ЧИСТО
структурный, без epsilon: same owner + same source face
(копланарность точна по построению RM1) + разделяющее ребро без
семантической нагрузки => merge, counted. Намеренные сплиты
(source-фолды, границы владельцев, классов) НЕ трогаются.
Никакого постфактум-хилинга готового меша.

**RM5 — Торцы.** У плотины и на alpha-reach — CAP-политика по
bands-оракулу (перпендикулярный торец в плоскости последней
грани). У полюса fan замыкается точкой (все rails сходятся в
вершине — торец вырожден, дырка невозможна по построению).

**RM5a — Виртуальный rail у станции-0 плотины (предписание по
стопу R1).** Плотина на старте (RR1-неоднозначность в
spine-вершине) не оставляет ленту без границы и не сужает её
(taper к нулю ЗАПРЕЩЁН). Вместо топологического rail строится
ВИРТУАЛЬНЫЙ — compile-static RailCapTrace: прямая трасса из
spine-станции в плоскости owner-грани; направление —
конструктивное (перпендикуляр к spine-ребру в плоскости грани
данной стороны) — детерминированная геометрия из семантических
входов, не «выбор». Границы виртуального rail: alpha_budget,
структурные границы (соседние channels/rails, любой spine,
плотины) и ПЕРВЫЙ не-копланарный fold — виртуальный rail не
пересекает сгибы (второсортность по построению). CAP-политика
RM5 применяется к его концу как обычно. Область применения в
R1 — PLANAR-owner; станция-0 плотина на криволинейной
поверхности до R3 — stop-условие. Примечание по полю
(walls.010: 298 DAM из 341 маршрутов): на PLANAR-регионах
виртуальные rails — ШТАТНО доминирующий случай, геометрия
плоскости от русла не зависит; топологические rails несут
нагрузку на кривизне (R3).

**RM6 — Углы spine.** Углы между сегментами spine — по
bands-оракулу, но ТОЛЬКО для in-plane составляющей поворота;
dihedral-составляющая (перегиб через ребро) обрабатывается
руслом бесплатно (RM1). У crest-углов (in-plane ~ 0) V-клин
структурно не рождается (поглощает C8.7).
**Объём RM6 в R1 (предписание по стопу):** полная surface-native
материализация пяти политик bands-оракула в R1 НЕ выполняется —
урок A12 (не совмещать переделку углов с большим рефакторингом);
runtime dynamic bands остаётся EXPERIMENTAL/OFF. В R1:
(a) dihedral-составляющая уходит в русло (RM1) — этого достаточно
для V2; (b) in-plane составляющая обслуживается СТАБИЛЬНОЙ
production-геометрией углов (A10-класс), применённой только к
in-plane повороту; (c) corner ownership/provenance тегируется
для будущей bands-работы; (d) полный bands surface-native —
отдельный срез ПОСЛЕ R3, решением ревьювера.

## 4. Правила конкуренции RC (freeze в станциях)

**RC1 — Станционная метрика.** Конкуренция потоков решается
сравнением накопленной rail-длины (станционной дистанции) до
спорной зоны. Равенство дистанций — граница проходит по
общему ребру/вершине русла; owner атрибутируется по
каноническому порядку chain id (структурный tie-break,
существующий канон; не числовой).

**RC2 — Spine-граница.** Чужой spine — абсолютная граница
потока (RR5a). Два потока, разделённые spine, не конкурируют
через него.

**RC3 — Freeze (S1).** Столкнувшаяся граница фиксируется в
станционных ключах; изменение ширины НЕ пересчитывает её
(инвариант «Static Interior» в rail-координатах). Регрессия
«ползущей сетки» — обязательная фикстура RF7.

**RC4 — Роль 2D-диаграммы.** Классический 2D-Voronoi/chart
сохраняет роли: admission (G3, качество UV), UV-параметризация,
и разрешение углов in-plane (RM6). Геометрию лент он больше НЕ
порождает. Любая ситуация, где станционная метрика не даёт
ответа, — stop-условие (не импровизировать 2D-фоллбэк).

## 5. Инварианты (сводка соответствия acceptance-матрице)

1. S1: трассировка/станции компайл-статичны; drag не меняет
   русла и замороженные границы.
2. Детерминизм: бит-идентичная регенерация; инвариантность к
   порядку перечисления рёбер/выделения.
3. Ноль численных выборов поведения: только топология,
   provenance, разметка.
4. Покрытие: русла между смежными rails — без дыр и без
   двойного покрытия; merge/плотины counted.
5. Provenance тотальна: каждый эмитируемый элемент знает свою
   source-грань, source-ребро, rail и станцию (уроки A-INT/GL).
6. Preview == confirm по геометрии (единый evaluator).

## 6. Контрольные фикстуры RF (ожидаемые исходы — acceptance)

- **RF1 Стена с аркой (полевой тест 3):** транс-срез ленты на
  junction'е лежит вдоль соседнего chain'а; ноль V-клиньев на
  crest-углах; поперечные пары соединены; ноль лишних сплитов
  на плоскости (после RM4).
- **RF2 UV-сфера, seam-кольцо:** русла — меридианные loops,
  лента облегает купол, CAP у полюса; ноль юбок.
- **RF3 Полюс:** rails сходятся в вершине, fan замыкается
  точкой, дырки нет.
- **RF4 Триангулированная вставка:** плотина на входе, видимый
  стоп (counted); с rail-mark — течение сквозь.
- **RF5 Вершина валентности 5:** плотина; с mark — мост.
- **RF6 Слияние rails:** merge-станция, клин русла закрыт, без
  дыр/overlap.
- **RF7 Встречные потоки (кольцо против кольца на цилиндре):**
  станционное деление, freeze при столкновении, S1 при drag
  (граница не ползёт).
- **RF8 Негатив:** rail-mark, ведущий в чужой spine, —
  терминация на spine (граница сильнее разметки).
- **RF11 Boundary-rail на конце spine (полевой тест 5, скрин 1):**
  seam-цепочка в поперечном направлении становится принудительным
  rail; торец ленты скользит вдоль неё; угловое русло по RM7 без
  митиринга.
- **RF12 Арка: «скользящие рёбра» у краёв ленты (тест 5, скрины
  3-4):** после триажа RD-1 внутри ленты нет функционально
  необъяснённых продольных рёбер-полосок; регрессия по скринам.
- **RF13 Building: валидация по footprint + fold-берега (стопы
  R1.1):** выбранные seams (412/504/553 + boundary 476/598)
  компилируются и материализуются при наличии вне footprint грани
  с вырожденной fan-триангуляцией (face 277); валидная грань с
  коллинеарной fan-тройкой ВНУТРИ footprint материализуется
  (RV2); негатив: истинно вырожденная грань внутри footprint ->
  именованный fail. Итог маршрутизации: RAIL_PLANAR, НЕ
  RailUnsupported и НЕ Patch-fallback — building принимается в
  R1.1 (expected-fail до R3 остаётся только за настоящей
  кривизной, half_sphere). Boundary-rails на fold'ах работают
  общими берегами (RR8a): pieces атрибутированы по секторам,
  станции route общие, сварка угла по общим ключам.
- **RF14 Building: multi-spine вершина 231 (RR1a):** секторные
  rails 417/472 созданы, start-DAM route и
  `RAIL_GEOMETRY_VIRTUAL_CAP_EMPTY` не возникают; угловые русла
  обеих стен материализуются; boundary 598 — единый route (ни
  одно его ребро не входит в другие routes — ассерт); сварка
  углов по общим RM1-ключам; итог building: RAIL_PLANAR.
- **RF15 Building: spine-spine угловой сектор v153 (RR1b):**
  сектор между spine 504/553 с >= 2 внутренними рёбрами уходит в
  corner-путь RM6 (A10 in-plane); dam-route 7 и
  `RAIL_GEOMETRY_VIRTUAL_CAP_EMPTY` не возникают; оба смежных
  русла закрыты угловой геометрией; ИТОГ building: RAIL_PLANAR,
  Patch fallback запрещён. Синтетический негатив RM5a-деградации:
  spine+boundary плотина с перпендикуляром вне owner-face -> cap
  по первому внутреннему ребру сектора, без fail и без taper.
- **RF10 Планарный L-поворот (in-plane 90 град.):** стабильная
  A10-семантика угла сохранена в rail-материализации (miter-стык
  как в production); differential пересдаётся осознанно.
- **RF9 Reversed enumeration:** RF1-RF7 при обратном порядке
  рёбер — бит-идентичный результат.

## 7. Stop-условия TRANCHE R

- Потребность в ЛЮБОМ числовом tie-break — стоп (дизайн-вопрос
  ревьювера).
- Конфликт с bands-оракулом или admission-оракулом — стоп.
- Станционная метрика не разрешает конкуренцию (RC4) — стоп.
- Неоднозначность семантики merge на эмиссии — стоп.
- Автономная замена правил RR/RM/RC «более удобными» запрещена.

## 8. Связь с существующим планом

- G1.2 (imprint-пары) и C8.7 (V-клин) — ПОГЛОЩЕНЫ RM1/RM6.
- G2 (облегание сферы) — ПОГЛОЩЁН RF2/RM1-RM5: геометрия
  облегания больше не требует intrinsic-admission.
- G3 (measured admission) — остаётся для КАЧЕСТВА UV
  (chart-слой), не для геометрии.
- Legacy SEAMS backend удалён из production routing по прямому решению
  пользователя. Неподдержанный rail/chart component остаётся явным
  `Failed`, а не материализуется старой сетью или miter-пайплайном.
- Атлас/GL/E-acceptance — пересматриваются ПОСЛЕ R: часть
  атласной сложности может стать ненужной (chart строится из
  rail-домена).
