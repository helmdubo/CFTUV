# Rail-оракул: русла течения декалей (TRANCHE R)

Статус: **APPROVED — утверждено пользователем; документ является каноном.**
Происхождение: полевые тесты 3-4 (SN-принцип, «берега русла»),
требование пользователя: только детерминированные топологические
правила, никаких эвристик и подбора чисел.

Runtime status: **R0 + R1 IMPLEMENTED** (`ed20953`, `572198e`,
`21d9d6e`) — RR1-RR7 компилируются в immutable rail-plan, а строгий
`RAIL_PLANAR` материализует принятые PLANAR-компоненты по RM1-RM3,
RM5/RM5a и ограниченному R1-контракту RM6. Shared semantic keys
получают единственный канонический offset-lift без spatial post-weld.
R2-R4 ещё не подключены; конкурирующие, криволинейные и неподдержанные
компоненты остаются на production Patch/chart пути. Автоматическая и
локальная Blender-проверка R1 зелёные; финальная полевая приёмка §0d
ожидает подготовленную пользователем сцену.

Роли слоёв (пивот архитектуры):
- **Rail-домен — единственный источник ГЕОМЕТРИИ ленты.**
- **Конкуренция (Voronoi-роль) — в станционной метрике русел:**
  кто владеет спорной зоной, где freeze.
- **Chart/UV — строится ИЗ rail-домена** (один источник, много
  читателей — урок GL закладывается с первого дня).
- Числа в системе — только СЕМАНТИКА (ширина, квант B0, бюджет
  G3). Все ВЫБОРЫ ПОВЕДЕНИЯ — топология, provenance, разметка.

## 1. Определения

- **Spine (хребет)** — выделенная цепочка seam-рёбер (pChain),
  источник ленты.
- **Rail (берег)** — путь рёбер меша, по которому фронтир течёт
  от spine в глубину поверхности.
- **Rail-станция** — вершина на rail с накопленной длиной рёбер
  от spine (compile-факт).
- **Русло (channel)** — полоса граней между двумя соседними
  rails.
- **Плотина (dam)** — детерминированная остановка rail на
  топологической неоднозначности.
- **Rail-mark** — явная пометка ребра артистом («мост» через
  неоднозначность).
- **Полюс** — вершина, в которой сходятся несколько rails
  (N-fan без единственного продолжения).
- **Торец** — срез начала/конца ленты, отвечающий за ширину
  (регулируется в preview-drag); скользит вдоль терминального
  rail своей вершины (RR9/RR9a).

## 1a. RP — Rails живут на изломах (поправка пользователя, тест 6;
КОРНЕВАЯ: снимает причину стопов 3-7)

**RP1 — Определение уточнено.** Rail — всегда ИЗЛОМ геометрии:
он разделяет грани, лежащие в РАЗНЫХ плоскостях (fold), либо ведёт
поток по кривизне (сфера, труба, арка). ВНУТРИ копланарного
региона rails НЕ СУЩЕСТВУЮТ и не трассируются: топология меша в
плоскости не несёт геометрической информации, и декаль скользит
in-plane аналитически от выбранного ребра — как в
production-планарной механике (A10-класс): перпендикулярная
экструзия от spine, углы по RM6a corner-paths (они — in-plane
аналитика и ОСТАЮТСЯ), конкуренция in-plane, boundary
pChains — принудительные границы-клипы (скольжение вдоль,
полевые тесты 4-5). Плотины/капы от триангулированной ПЛОСКОЙ
топологии не возникают вовсе; rails подсвечиваются только на
изломах. Проверка RP-оверлея — на канонических объектах §0d.3b:
wall_noise_top / rounded_wall_noise_top (rails только на реальных
фолдах шумного верха), чисто планарная стена — routes=0 (это
КОРРЕКТНЫЙ RP-исход, walls.001 подтвердил).

**RP2 — Предикат копланарности.** Существующая
PLANAR-классификация analysis-слоя (канонический предикат системы
с эпохи backend routing). НОВЫХ epsilon не вводится.

**RP3 — Скоупинг правил.** RR1a/RR1b (сектора и счёт внутренних
рёбер), RM5a (виртуальный rail/структурный cap) и RM7a
(`RailAngularChannel`) применяются ТОЛЬКО к несопланарным веерам
— это территория кривизны (R3). Для копланарных вееров внутренние
рёбра НЕ считаются (изломов нет — нет структуры): spine-spine
веер -> in-plane угол RM6a/A10; веер с boundary pChain ->
in-plane клип линией цепочки со сваркой по станционным ключам
boundary-route. RR8/RR8a без изменений: pChain — принудительная
граница в ОБОИХ режимах (на fold'е — rail-route; в плоскости —
клип-линия; станции цепочки едины в обоих случаях).
`RailAngularChannel` (RM7a) паркуется как R3-примитив.
Перпендикулярная трасса RM5a в плоскости — не «деградация», а
штатная in-plane граница потока.

**RP2a — Два допуска, две роли (директива по ревью R1.2).**
Вокруг «плоскостности» в системе РОВНО ДВЕ константы, и их роли
не пересекаются:
- `DECAL_COPLANAR_DOT` — ЕДИНСТВЕННЫЙ семантический предикат
  излома (RP2): что считается fold'ом для маршрутизации, RR9(b),
  границ RM5a и классификации seam/corner. Значение — СЕМАНТИКА
  (класс width/B0/G3-бюджета): текущее cos(4 град.) (R1.2,
  `d0a8d6d`; прежнее ~8.1 град.). Смена значения — только
  дизайн-решение ревьювера/пользователя, фиксируемое в оракуле;
  кандидат на пользовательский параметр («чувствительность к
  изломам») после R4. Тюнинг значения под прохождение фикстур
  запрещён.
- `_RAIL_PLANAR_DOT` (1-1e-10) — НЕ предикат излома, а допуск
  арифметической ПРЕДСТАВИМОСТИ одной плоскости (граница
  возможностей R1-геометрии). Разрешённые употребления: guard с
  именованным fail (`SOURCE_FACE_NON_PLANAR`,
  `CURVED_OWNER_UNSUPPORTED`, ...) либо именованная counted
  терминация (FOLD в `RailCapTrace`). ЗАПРЕЩЕНО использовать его
  для ВЫБОРА альтернативной геометрии или маршрута.
- Щель (представимость, 4 град.): маршрутизация считает пару
  копланарной, а R1-геометрия не может представить её одной
  плоскостью. Исход в щели ОБЯЗАН быть именованным
  стопом/терминацией, никогда — тихим поведением; щель
  ПОГЛОЩАЕТСЯ R3 (кривизна). Это не «два представления одного
  объекта»: предикаты отвечают на разные вопросы (семантика
  излома vs арифметическая представимость).

## 2. Правила трассировки RR (только топология; скоуп — изломы и
кривизна, см. RP)

**RR1 — Старт.** На каждой вершине spine, на каждой стороне,
rail стартует из ЕДИНСТВЕННОГО ребра, общего для двух граней
этой стороны, инцидентных spine-рёбрам вершины (регулярный
quad-стык). Нет единственности (fan из 1 или >2 граней, missing
quad) — плотина на старте либо rail-mark.

**RR1a — Секторные старты на multi-spine/boundary вершине
(директива по третьему стопу R1.1, building vertex 231).**
На spine-вершине веер граней band-стороны РАЗДЕЛЯЕТСЯ
делимитерами — spine-рёбрами и boundary-rails (RR8) — на СЕКТОРА
(максимальные пробеги веера между делимитерами). Правило RR1 —
частный случай для прямой вершины (один сектор через оба
spine-ребра). Обобщение, по сектору:
- ровно ОДНО внутреннее ребро веера -> обычный rail стартует из
  него (стандартная трассировка RR2 дальше; это полноценный route
  в routing IR со своими станциями);
- НОЛЬ внутренних рёбер -> rail не нужен: единственная грань
  сектора — угловое русло, ограниченное делимитерами напрямую
  (вырожденный RM7-клин);
- >= 2 внутренних рёбер -> плотина на старте сектора / rail-mark
  (RR3-семантика), далее RM5a.
Building v231: сектор стены A = (77, ребро 417, 167) -> rail по
417; сектор стены B = (149, ребро 472, 300) -> rail по 472; грани
77/149 присвоены, start-DAM и пустой virtual cap не возникают.
Уточнение RM7: с секторными rails «угловое русло» — ОБЫЧНОЕ русло
между секторным rail и boundary-rail;специальный случай RM7
остаётся только для сектора без внутренних рёбер.
Инварианты против второго представления boundary (ответ на
вопрос 3): (i) рёбра boundary-цепочки принадлежат ИСКЛЮЧИТЕЛЬНО
boundary-route — никакой другой route не может их содержать;
(ii) станции boundary-route считаются один раз (RR8a); секторные
rails имеют СВОИ станции по своим рёбрам; (iii) сварка углового
русла с boundary — по общим source-face/vertex ключам RM1, без
переноса станций. Вариант «bridge pieces назад по вееру внутри
boundary-route» ОТКЛОНЁН: контрабанда структуры русла в 1D-rail,
второсортное представление того, что является руслами и rails.

**RR1b — Классификация секторов по делимитерам (директива по
четвёртому стопу R1.1, building vertex 153; признание: третья
ветвь RR1a была неполна — не различала тип делимитеров).**
- **Сектор spine-spine** (оба делимитера — spine-рёбра):
  1 внутреннее ребро -> обычный rail (классический RR1);
  0 или >= 2 внутренних рёбер -> УГЛОВОЙ СЕКТОР -> обслуживается
  corner-путём RM6 (в R1 — стабильная A10-геометрия in-plane
  поворота), который и ЗАКРЫВАЕТ оба смежных русла. Dam-route НЕ
  создаётся, RM5a НЕ вызывается — cap не нужен, закрытие даёт
  угловая геометрия. Building v153 — ровно этот случай: выход
  конструктивного перпендикуляра за owner-face при r>0 — симптом
  того, что сектор угловой, а не rail-ambiguity. Численного
  критерия «угол против прямой» НЕ вводится: классификация
  только по числу внутренних рёбер и типу делимитеров.
- **Сектор spine+boundary / spine+border**: прежние правила RR1a
  (1 -> rail; 0 -> вырожденный RM7; >= 2 -> плотина + RM5a).

**RM5a-деградация (структурный cap).** Если для ЛЕГАЛЬНОГО
RM5a-случая (сектор spine+boundary/border) конструктивный
перпендикуляр покидает owner-face уже при r>0 (точный
геометрический факт, без допусков), cap следует СТРУКТУРНОЙ
границе: первому внутреннему ребру сектора, смежному с гранью
spine-ребра данной стороны — топологично, единственно,
surface-native (лента честно заканчивается по ребру меша).
Запрет «выбора направления» не нарушен: ребро — факт топологии,
не подбор. Taper к нулю по-прежнему запрещён.

**RR2 — Продолжение.** Из вершины rail продолжается в ребро, НЕ
делящее грань с входящим ребром (edge-loop правило), и ТОЛЬКО
если такое ребро единственно (регулярная валентность-4 вершина).

**RR3 — Плотина.** Ноль или >= 2 кандидатов продолжения —
детерминированный стоп: станция-плотина. Событие counted и
видно в подсветке русла. Запрещены: угловые критерии, выбор по
индексам/длинам, любой численный tie-break.

**RR4 — Разметка-мост.** Помеченное артистом ребро (rail-mark),
инцидентное текущей вершине, продолжает rail через
неоднозначность. Разметка + топология = полная спецификация
течения; больше НИЧТО на выбор не влияет.

**RR5 — Границы (терминация).** Rail завершается при:
(a) достижении вершины любого spine (своего или чужого) —
граница: поток НЕ пересекает spine, транс-срез ленты скользит
вдоль него (полевой кейс стены);
(b) полюсе (N-fan без единственного продолжения);
(c) исчерпании alpha_budget по накопленной длине (параметр
ширины — семантика, не эвристика);
(d) плотине (RR3).
Граница (a) сильнее разметки: rail-mark, ведущий в spine,
терминируется на spine (негативная фикстура RF8).

**RR6 — Слияние rails.** Два rail'а, пришедшие в одну вершину, —
merge-станция: русло-клин между ними закрывается, дальше течёт
один rail (по RR2 от вершины слияния). Детерминированное
топологическое событие, counted.

**RR8 — Принудительные boundary-rails (полевая поправка, тест 5).**
Seam-ребро (любой pChain, выбранный или нет), инцидентное
spine-вершине и НЕ принадлежащее самому spine, — ПРИНУДИТЕЛЬНЫЙ
boundary-rail с ВЫСШИМ приоритетом (над RR1/RR2): фронтир
скользит вдоль него, он одновременно граница и направляющая
(«берег» в буквальном смысле — полевой скрин: синие стрелки из
конечной вершины spine). Продолжение boundary-rail — вдоль его
СОБСТВЕННОЙ seam-цепочки (топологическое продолжение цепочки),
не quad-loop. Терминация: alpha_budget по накопленной длине,
конец цепочки (дальше — плотина/CAP), встреча другого spine.
Уточнение RR5(a): «терминация на вершине spine» относится к
rail, встречающему spine ПОПЕРЁК; seam-ребро, идущее В
направлении расширения ленты, — не терминатор, а сам rail.

**RR9 — Терминальные rails: скольжение торцов (полевой тест 7).**
Полевой факт: rails из торцевых вершин spine трассируются верно,
но ТОРЦЫ ленты (начало/конец) режутся по старой перпендикулярной
семантике и не следуют этим rails. Правило: торцевой срез ленты на
каждой стороне СКОЛЬЗИТ вдоль терминального rail торцевой вершины,
по иерархии (детерминированной, без чисел):
(a) boundary pChain (существующий RR8 — частный случай);
(b) ЕДИНСТВЕННОЕ fold/border-ребро в веере данной стороны торцевой
    вершины (RP-излом: пара несопланарных граней, либо
    border-ребро) -> торец следует его цепочке (продолжение — по
    той же дисциплине, что rails: только при топологической
    единственности; стоп -> дальше существующая CAP-семантика),
    станции вдоль rail, длина до alpha;
(c) нет fold/border-ребра либо неоднозначность (>= 2 кандидатов
    без разметки) -> перпендикулярный in-plane клип (штатный
    планарный случай RP — в плоскости следовать нечему).
Материализация ОБЯЗАНА читать терминальный rail из rail-плана
(«один источник»): повторная деривация направления торца
запрещена. Rail-mark применим как мост и здесь.

**RR9a — Перпендикулярный снэп терминального направляющего
(поправка пользователя, скрины с синими стрелками после R1.2).**
Полевое подтверждение: терминальные seam-рёбра — rails в рамках
своего планарного patch (существующие RR8/RP3, скрины
соответствуют канону). НОВОЕ — разрешение неоднозначности уровня
(a): если из конечной вершины выделенного spine выходит НЕСКОЛЬКО
seam-рёбер, лежащих в patch данной стороны, направляющим
терминального среза выбирается кандидат, БЛИЖАЙШИЙ к
каноническому перпендикуляру — in-plane перпендикуляру к
терминальному spine-ребру в конечной вершине (ТО ЖЕ направление,
что у фолбэка (c) и RM5a: один источник).
Дисциплинарная квалификация: это НЕ угловой критерий трассировки
(запрет RR3 для продолжений в силе) и НЕ настраиваемое число —
это СНЭП уже существующего канонического направления среза к
ближайшему дискретному принудительному кандидату: аргмин по
конечному множеству, без порогов и epsilon. Точная ничья двух
кандидатов -> плотина + rail-mark (RR3-семантика); rail-mark
СИЛЬНЕЕ снэпа (выбор артиста). Статус rail'ов не меняется: ВСЕ
seam-кандидаты остаются принудительными границами (RR8), снэп
выбирает только НАПРАВЛЯЮЩЕГО торца. Продолжение выбранного —
вдоль его собственной цепочки (RR8); ветвление цепочки дальше по
ходу — плотина, снэп повторно НЕ применяется.
**Финальная структура (итоговое уточнение пользователя).**
Первый вопрос — планарен ли patch (RP-предикат):
- **ПЛАНАРНЫЙ patch:** направляющие — ТОЛЬКО внешние seam-рёбра,
  примыкающие к выделенным через общие вершины («линии паутины»);
  простые рёбра меша игнорируются и rails НЕ становятся (RP1);
  нет seam-кандидатов -> торец движется перпендикулярно
  выбранному ребру (фолбэк (c)).
- **КРИВОЛИНЕЙНЫЙ patch (вогнутый/выпуклый):** внешние
  примыкающие seam-рёбра — ТАКЖЕ rails, по которым ползёт
  декаль; ПЛЮС простые примыкающие рёбра становятся rails в
  рамках предиката копланарности (уровень (b)/RP — изломы); снэп
  применяется И ЗДЕСЬ: несколько внешних seam-цепочек из общей
  вершины -> выбирается ближайшая к перпендикуляру выбранного
  seam-ребра этой вершины.
Единый инвариант: внешние pChains, примыкающие к выделенным, —
ВСЕГДА rails (RR8 без изменений); единственная неоднозначность,
решаемая отбором, — несколько цепочек из одной вершины, и отбор
назначает лишь НАПРАВЛЯЮЩЕГО торца (не-выбранные кандидаты
остаются принудительными границами-клипами).
Каноническая мера снэпа (едина для обоих режимов). Семантика (со
слов пользователя): «перпендикуляр» — условный термин, эталон —
направление, куда двигал бы декаль СТАРЫЙ волновой механизм
(фронт волнами от выбранного ребра, тип 2D skeleton).
Формализация: argmin |dot(unit(кандидат), unit(терминального
spine-ребра))| в 3D — без выбора касательной плоскости и
усреднения нормалей; на планарном patch совпадает с направлением
волнового фронта. Точная ничья -> плотина + rail-mark.
Примечание реализации: на криволинейных patches правило вступает
в силу вместе с R3-материализацией (до неё кривизна — именованный
стоп); селектор ОДИН на оба режима — отдельного «кривого»
механизма не существует. R3 может уточнить механику обёртывания
(оговорка пользователя о сфере), но принцип «примыкающие pChains —
всегда rails; неоднозначность — отбор одной цепочки» — канон.
Определение: **торец** — срез начала/конца ленты, отвечающий за
ширину, регулируемую в preview-drag; его движение — скольжение
вдоль терминального rail по станциям (S1: rail-план
компайл-статичен, drag меняет только extent).

**RR10 — Нити между chains (топологическая закономерность
пользователя, после теста 7).** НИТЬ — ребро меша, НЕ
принадлежащее ни одному pChain, оба конца которого — spine-вершины
ДВУХ РАЗНЫХ pChains в рамках одного patch. На НЕПЛАНАРНОЙ
поверхности (скоуп RP: изломы/кривизна) нить — принудительный
rail-направляющая. В копланарном регионе такое ребро rail'ом НЕ
становится (RP1 без изменений: в плоскости — in-plane аналитика).
(a) **Прямое распознавание.** Статус нити — прямой топологический
    факт (оба конца на spine-вершинах разных цепочек), НЕ зависящий
    от того, открыла бы её трассировка RR1/RR2: нить признаётся
    rail'ом даже там, где регулярный quad-старт её не находит.
(b) **Селектор при неоднозначности.** В вершине, где RR1/RR1a/RR3
    видят >= 2 кандидатов, РОВНО ОДИН кандидат-нить выигрывает —
    это детерминированный топологический селектор, не численный
    tie-break; >= 2 нитей-кандидатов — плотина, как раньше
    (rail-mark применим). Иерархию не меняет: spine и boundary
    pChain (RR8) остаются старше нити.
(c) **Одна сущность — два чтения станций.** Нить — ОДИН route
    (одна геометрия, один набор ключей), общий берег ОБОИХ потоков
    (дисциплина RR8a). Станционные ЗНАЧЕНИЯ — пофлотовые факты:
    поток из chain A меряет накопленную длину от A, поток из B —
    от B. Это два ЧТЕНИЯ одного источника, не два представления;
    второй route на ту же кривую запрещён.
(d) **Freeze-локус (R2).** Встреча потоков вдоль нити решается
    станционной метрикой RC1 по двум чтениям (c); при равенстве —
    граница по общей вершине/ребру, tie-break канонический
    структурный (chain id). Замороженная граница живёт в
    станционных ключах нити (RC3, S1).
(e) **Многорёберные нити.** Rail, трассированный по RR2 и
    терминированный на чужом spine (RR5(a)), — многорёберная нить:
    получает тот же статус (c)/(d) ретроактивно. Прямое
    распознавание (a) применяется ТОЛЬКО к одиночным рёбрам:
    поиск путей между цепочками ЗАПРЕЩЁН (выбор пути из многих —
    скрытая эвристика).

**RM7 — Угол у конца spine (стык с boundary-rail): простой
вариант.** Угловое русло (веер граней между последним обычным
rail и boundary-rail) материализуется по граням источника как
обычное русло, БЕЗ диагонального митиринга. Митиринг — вопрос
UV-слоя (R4) и/или bands-среза после R3; решение ревьювера по
текстурированным полевым скринам, не заранее.

**RM6a — Corner-path: контракт интеграции A10 с RR1b-сектором
(директива по пятому стопу R1.1, building v153).**
1. **Новый вид пути в geometry IR: `CORNER` boundary-path** — по
   одному на каждую тройку **(угловая вершина, смежное
   spine-ребро, СТОРОНА ленты)** — поправка по шестому стопу
   (RF10): исходный ключ без стороны был недоспецифицирован
   (признано). Обоснование кардинальности: на manifold-вершине
   пара spine-делимитеров режет веер РОВНО на две дуги — по одной
   на сторону ленты; сторона уже канонична в системе (стороны
   цепочек/русел), сектор наследует её от своей дуги веера. Каждый
   corner-path — ОДНОСТОРОННИЙ полуперпендикуляр со своим
   неотрицательным r (домен (s, r) не меняется). RF10
   quarter-join: ЧЕТЫРЕ corner-path в v12 — (v12,114,out),
   (v12,114,in), (v12,122,out), (v12,122,in). Отклонено: signed-r
   двунаправленный path (сцепляет два семантически независимых
   интерфейса, ломает неотрицательный домен, clipping и
   UV-side); отдельная INNER_DIVIDER-семантика для zero-сектора
   (дублирует то, что выражают односторонние corner-paths —
   граничная сущность едина, различается только ЗАПОЛНЕНИЕ:
   convex-сторона — клин между срезами, concave — стык по
   стабильной A10-политике).
   Геометрия: конструктивный перпендикуляр к ЭТОМУ spine-ребру в
   ПЛОСКОСТИ сектора (R1: сектор коплан — факт routing IR), от
   вершины до alpha_budget, структурно клиппится материей сектора.
   Это НЕ route (нет source-ребра, станций, RR-трассировки — и
   потому не несёт route id) и НЕ CAP (обе стороны имеют материю:
   это ИНТЕРФЕЙС сегментной ленты и углового клина). Пересечение
   внутренних КОПЛАНАРНЫХ рёбер веера при r>0 — штатно: в
   плоскости это не фолды; синтетический CAP и синтетический
   ROUTE отклонены (верно распознаны исполнителем как нарушения
   RM5a-семантики и провенанс-тотальности).
2. **Owner = МНОЖЕСТВО sector faces из routing IR.** Flood-домен
   `_compile_outer_corner_cells()` задаётся множеством граней
   сектора (RR1b) напрямую — никакого выбора seed среди
   коплан-кандидатов: выбор запрещён и не нужен, множество
   устраняет сам вопрос. Некопланарная грань в секторе —
   именованный R1-стоп (residual-объём).
3. **Provenance corner-path**: ключ = (id угловой вершины, id
   смежного spine-ребра, сторона ленты). Геометрия среза считается ОДИН раз;
   обе стороны — сегментное русло и угловой клин — ссылаются на
   ОДИН объект и свариваются его квантованными r-ключами («один
   источник, много читателей»). Грань, разрезаемая срезом
   (building face 77), имеет двойное членство, разрешаемое ПО
   КУСКАМ провенансом; RM4 через corner|segment интерфейс НЕ
   мёржит (семантическая граница).
4. **Заполнение клина** между двумя corner-paths угловой вершины —
   стабильная A10-политика (RM6, R1-объём) над плоскостью
   сектора.
5. `_path_for_endpoint()` для endpoint'ов секторов класса CORNER
   возвращает corner-path; `_route_for_face()` для них не
   вызывается.

**RM7a — Угловое русло как примитив: `RailAngularChannel`
(директива по седьмому стопу R1.1, building v231).**
1. **Новый примитив geometry IR** для RM7-русла (клин между двумя
   paths, стартующими в одной spine-станции): `RailAngularChannel`.
   НЕ обычный `RailChannel` с вырожденным интервалом — веер и
   лестница структурно различны, и вырожденный интервал породил бы
   скрытые нарушения предположений интервального кода; НЕ
   `RailCornerCell` — «cell» коннотирует планарный полигон, клин в
   общем случае многогранен.
2. **Параметризация**: apex s = станция угловой вершины на spine
   ДЕЛИМИТЕРА сектора (v231 на цепочке 553 для клина 167; на 412
   для клина 300); оба берега делят этот единственный s; r каждого
   берега — по СОБСТВЕННЫМ станциям его path (417 и 598; 472 и
   598; станции 598 едины по RR8a). Интерьер — RM1
   source-face/vertex ключи; alpha-фронтир поперёк клина строится
   по-гранево между alpha-точками двух берегов (существующая
   пер-грань механика фронтира).
3. **Provenance**: spine_edge_id = spine-делимитер сектора;
   side = сторона сектора (канон RM6a); собственного
   source-edge интервала НЕТ — вместо него ссылка на
   sector-запись routing IR (угловая вершина, пара делимитеров,
   грани). Сварка: с соседним регулярным руслом — по станционным
   ключам общего секторного rail (417/472), через boundary — по
   станционным ключам единого 598.
4. **Взаимоисключение с RM6-partition**: cross-fold
   `_compile_corner_partitions` между двумя spine-руслами НЕ
   строится для вершины-стороны, у которой RR1a-сектора ПОЛНОСТЬЮ
   покрывают веер (закрытие дают angular-русла + boundary-route).
   Условие структурное; ассерт «ровно один механизм на
   вершину-сторону»: оба или ни одного — именованный fail, не
   тихое смешение. Частичное покрытие веера секторами —
   именованный fail. Этим `RAIL_GEOMETRY_CURVED_OWNER_UNSUPPORTED`
   на v231 исчезает структурно: попытка A10 через fold просто не
   выполняется.

**RR8a — Ownership boundary-rail на fold'е (директива по второму
стопу R1.1, building).** Boundary-rail — ОДНА топологическая
1D-сущность на seam-цепочку: её станции считаются ОДИН раз
(«один источник, много читателей»). Owner — НЕ свойство rail, а
атрибуция его PIECES относительно каждого смежного
face-sector/русла: для материализации русла на стороне X
участвуют только куски rail, граничащие с гранями стороны X;
дальняя сторона fold'а НЕ участвует и НЕ МОЖЕТ дисквалифицировать
route (building: pChain 476 на ребре стен 79|149 под 90 град. —
легальный общий берег обоих секторов; pChain 598 с key-гранями
двух ориентаций — берег ДВУХ русел одной декали, по куску на
сектор). Residual-запрет `RAIL_GEOMETRY_CURVED_OWNER_UNSUPPORTED`
(R1-объём) применяется только там, где выходит за R1 сама
МАТЕРИАЛИЗУЕМАЯ сторона route (его собственные support-грани);
наличие не-копланарной грани по ту сторону rail — никогда не
причина отказа. Вариант «route на каждый face-sector» ОТКЛОНЁН:
два route на одну физическую кривую = «два представления одного
идеального объекта» — класс болезни, истреблённый в проекте
(двойные квантизации станций разорвали бы сварку угла); общность
станций достигается единственностью route, а не синхронизацией
дубликатов.

**RR7 — Компайл-статичность (S1).** Трассировка и станции
вычисляются на compile до alpha_budget и НЕ зависят от текущей
ширины drag. Drag меняет только материализованный extent вдоль
уже трассированных русел. `Construct()`/трассировка в кадре
запрещены.

**RV1 — Область валидации source-геометрии (директива по стопу
R1.1, полевой building).** Валидация следует материализации:
fail-fast применяется РОВНО к footprint скомпилированного
rail-плана — support-грани русел (обычных, виртуальных RM5a и
угловых RM7) до alpha_budget плюс грани, участвующие в
RR-решениях у spine-вершин. Footprint — конструктивный
compile-факт (грани, которых лента коснётся), не «выбранные
patches» (слишком грубо и косвенно) и не весь PatchGraph.
Геометрия ВНЕ footprint не валидируется и НЕ МОЖЕТ провалить
компиляцию (counted-диагностика допустима, отказ — нет): игровой
ассет всегда содержит грязную грань где-то вдали, и инструмент не
должен быть её заложником. Внутри footprint отказ обязан называть
конкретную грань и причину.

**RV2 — SOURCE_TRIANGLE_DEGENERATE только для истинно вырожденных
граней.** Коллинеарная тройка в fan-триангуляции ВАЛИДНОЙ грани
(building face 277: 6-gon, area 36.65) — артефакт выбора pivot
триангулятора, не дефект меша: коллинеарные вершины на прямом
ребре — штатная топология игровых ассетов. Обрабатывается
робастной триангуляцией (пропуск нулевых fan-треугольников /
ear-clip), НЕ отказом. Отказ — только для истинно вырожденных
граней (нулевая площадь / все вершины коллинеарны), с именем
грани.

## 3. Правила материализации RM (surface-native)

**RM1 — Геометрия по граням source-меша.** Лента эмитируется по
руслам: каждый quad лежит в плоскости своей source-грани ПО
ПОСТРОЕНИЮ; перегибы наследуют source-рёбра. Поперечные пары
вершин (верх_i/низ_i) существуют автоматически — отдельный
imprint-шаг для SEGMENT-интерьеров отмирает (поглощает G1.2).

**RM2 — Координаты rail-домена (поправка по стопу R1;
первоначальная редакция содержала инверсию — признано).**
Внутренние координаты НЕЙТРАЛЬНЫ и именуются (s, r): s — станции
вдоль spine (существующая механика), r — накопленная длина рёбер
rail поперёк (измеренный факт). Публичный UV-контракт НЕ
переопределяется: bands-оракул и материализатор сохраняют
U — поперёк (u_frac * alpha), V — вдоль/phase. Отображение
(s, r) -> (U, V) выполняется ОДИН раз в R4 по существующему
контракту; слои R1-R3 оперируют только (s, r).

**RM3 — Сужение/расширение русла.** Rails сходятся/расходятся —
геометрия следует руслу как есть; компенсация — в UV-слое
(chart из rail-домена), не в геометрии.

**RM4 — Слияние на эмиссии (convex-сплиты).** Критерий ЧИСТО
структурный, без epsilon: same owner + same source face
(копланарность точна по построению RM1) + разделяющее ребро без
семантической нагрузки => merge, counted. Намеренные сплиты
(source-фолды, границы владельцев, классов) НЕ трогаются.
Никакого постфактум-хилинга готового меша.

**RM5 — Торцы.** У плотины и на alpha-reach — CAP-политика по
bands-оракулу (перпендикулярный торец в плоскости последней
грани). У полюса fan замыкается точкой (все rails сходятся в
вершине — торец вырожден, дырка невозможна по построению).

**RM5a — Виртуальный rail у станции-0 плотины (предписание по
стопу R1).** Плотина на старте (RR1-неоднозначность в
spine-вершине) не оставляет ленту без границы и не сужает её
(taper к нулю ЗАПРЕЩЁН). Вместо топологического rail строится
ВИРТУАЛЬНЫЙ — compile-static RailCapTrace: прямая трасса из
spine-станции в плоскости owner-грани; направление —
конструктивное (перпендикуляр к spine-ребру в плоскости грани
данной стороны) — детерминированная геометрия из семантических
входов, не «выбор». Границы виртуального rail: alpha_budget,
структурные границы (соседние channels/rails, любой spine,
плотины) и ПЕРВЫЙ не-копланарный fold — виртуальный rail не
пересекает сгибы (второсортность по построению). CAP-политика
RM5 применяется к его концу как обычно. Область применения в
R1 — PLANAR-owner; станция-0 плотина на криволинейной
поверхности до R3 — stop-условие. Примечание по полю
(walls.010: 298 DAM из 341 маршрутов): на PLANAR-регионах
виртуальные rails — ШТАТНО доминирующий случай, геометрия
плоскости от русла не зависит; топологические rails несут
нагрузку на кривизне (R3).

**RM9 — Terminal-bridge для production-пути (полевой стоп после
R1.3: «торцы всё ещё не двигаются по rails»).** Диагноз: RR9/RR9a
реализованы в материализаторе RAIL_PLANAR; объекты пользователя
(арка rounded_wall, sagging_wall) маршрутизируются на production
developable-путь (`PLANAR+INTRINSIC_DEVELOPABLE`), который
rail-план НЕ читает — терминальные выборы существуют в плане, но
их никто не потребляет. Правило (до R3): production-путь ОБЯЗАН
читать терминальные выборы торцов из скомпилированного rail-плана
(«один источник»; rail-план компилируется topology-only и на этих
мешах — R0-факт): торец скользит вдоль выбранной pChain/fold
цепочки по её станциям; фолбэк PERP — прежняя перпендикулярная
механика. Скоуп СТРОГО торцы: интерьер и углы production-пути не
трогаются («не сломать»); второго селектора/повторной деривации
не существует — потребление плана read-only. Если торцевая
механика production-пути не может выразить «скольжение вдоль
цепочки» без крупного рефакторинга — именованный дизайн-стоп.
После R3 контракт сохраняется (материализация читает план),
bridge отмирает вместе с production-путём.

**RM9-fix — Торец есть срез, не накладка (полевой стоп
пользователя: «нашлёпки», скрин edit-mode).** Реализация
`3d31a70` дала скольжение ОТДЕЛЬНЫМИ faces поверх ленты — двойное
покрытие терминальной зоны, нарушение инварианта 4. Причина —
ПРОТИВОРЕЧИЕ В ДИРЕКТИВЕ РЕВЬЮВЕРА (признано): «интерьер
бит-идентичен» и «торец скользит» одновременно невыполнимы для
концевых faces; исполнитель удовлетворил оба требования
наложением — единственным способом. Исправление канона:
1. Торец — СРЕЗ САМОЙ ЛЕНТЫ (граница её концевых faces), НЕ
   отдельный компонент-накладка. Скольжение = переразрез:
   граничные рёбра концевых faces ложатся НА терминальный rail;
   старая перпендикулярная граница при выбранном PCHAIN/FOLD-гиде
   НЕ СУЩЕСТВУЕТ. Зона между старым перпендикуляром и rail либо
   добавляется к ленте, либо отрезается от неё — срез ЗАМЕНЯЕТ
   перпендикуляр, а не дополняет его.
2. Запрет двойного покрытия применён к терминальной зоне явно:
   ни одна точка поверхности не покрыта более чем одним face
   декали; «нашлёпка» — именованный дефект (негатив RF19).
3. Скоуп бит-идентичности ИСПРАВЛЕН: неизменны faces, НЕ
   затронутые терминальным срезом; faces терминальной зоны
   меняются по определению среза.
4. Приёмочные скрины зон срезов ОБЯЗАНЫ включать wireframe /
   edit-mode ракурс: shaded-рендер маскирует дубли (полевой
   урок). Углы между сегментами spine — по
bands-оракулу, но ТОЛЬКО для in-plane составляющей поворота;
dihedral-составляющая (перегиб через ребро) обрабатывается
руслом бесплатно (RM1). У crest-углов (in-plane ~ 0) V-клин
структурно не рождается (поглощает C8.7).
**Объём RM6 в R1 (предписание по стопу):** полная surface-native
материализация пяти политик bands-оракула в R1 НЕ выполняется —
урок A12 (не совмещать переделку углов с большим рефакторингом);
runtime dynamic bands остаётся EXPERIMENTAL/OFF. В R1:
(a) dihedral-составляющая уходит в русло (RM1) — этого достаточно
для V2; (b) in-plane составляющая обслуживается СТАБИЛЬНОЙ
production-геометрией углов (A10-класс), применённой только к
in-plane повороту; (c) corner ownership/provenance тегируется
для будущей bands-работы; (d) полный bands surface-native —
отдельный срез ПОСЛЕ R3, решением ревьювера.

## 4. Правила конкуренции RC (freeze в станциях)

**RC1 — Станционная метрика.** Конкуренция потоков решается
сравнением накопленной rail-длины (станционной дистанции) до
спорной зоны. Равенство дистанций — граница проходит по
общему ребру/вершине русла; owner атрибутируется по
каноническому порядку chain id (структурный tie-break,
существующий канон; не числовой).

**RC2 — Spine-граница.** Чужой spine — абсолютная граница
потока (RR5a). Два потока, разделённые spine, не конкурируют
через него.

**RC3 — Freeze (S1).** Столкнувшаяся граница фиксируется в
станционных ключах; изменение ширины НЕ пересчитывает её
(инвариант «Static Interior» в rail-координатах). Регрессия
«ползущей сетки» — обязательная фикстура RF7.

**RC4 — Роль 2D-диаграммы.** Классический 2D-Voronoi/chart
сохраняет роли: admission (G3, качество UV), UV-параметризация,
и разрешение углов in-plane (RM6). Геометрию лент он больше НЕ
порождает. Любая ситуация, где станционная метрика не даёт
ответа, — stop-условие (не импровизировать 2D-фоллбэк).

## 5. Инварианты (сводка соответствия acceptance-матрице)

1. S1: трассировка/станции компайл-статичны; drag не меняет
   русла и замороженные границы.
2. Детерминизм: бит-идентичная регенерация; инвариантность к
   порядку перечисления рёбер/выделения.
3. Ноль численных выборов поведения: только топология,
   provenance, разметка. (RR9a-снэп — не численный выбор:
   аргмин дискретных кандидатов против уже существующего
   канонического направления, без порогов; точная ничья —
   плотина.)
4. Покрытие: русла между смежными rails — без дыр и без
   двойного покрытия; merge/плотины counted.
5. Provenance тотальна: каждый эмитируемый элемент знает свою
   source-грань, source-ребро, rail и станцию (уроки A-INT/GL).
6. Preview == confirm по геометрии (единый evaluator).

## 6. Контрольные фикстуры RF (ожидаемые исходы — acceptance)

- **RF1 Стена с аркой (полевой тест 3):** транс-срез ленты на
  junction'е лежит вдоль соседнего chain'а; ноль V-клиньев на
  crest-углах; поперечные пары соединены; ноль лишних сплитов
  на плоскости (после RM4).
- **RF2 UV-сфера, seam-кольцо:** русла — меридианные loops,
  лента облегает купол, CAP у полюса; ноль юбок.
- **RF3 Полюс:** rails сходятся в вершине, fan замыкается
  точкой, дырки нет.
- **RF4 Триангулированная вставка:** плотина на входе, видимый
  стоп (counted); с rail-mark — течение сквозь.
- **RF5 Вершина валентности 5:** плотина; с mark — мост.
- **RF6 Слияние rails:** merge-станция, клин русла закрыт, без
  дыр/overlap.
- **RF7 Встречные потоки (кольцо против кольца на цилиндре):**
  станционное деление, freeze при столкновении, S1 при drag
  (граница не ползёт).
- **RF8 Негатив:** rail-mark, ведущий в чужой spine, —
  терминация на spine (граница сильнее разметки).
- **RF11 Boundary-rail на конце spine (полевой тест 5, скрин 1):**
  seam-цепочка в поперечном направлении становится принудительным
  rail; торец ленты скользит вдоль неё; угловое русло по RM7 без
  митиринга.
- **RF12 Арка: «скользящие рёбра» у краёв ленты (тест 5, скрины
  3-4):** после триажа RD-1 внутри ленты нет функционально
  необъяснённых продольных рёбер-полосок; регрессия по скринам.
  **Триаж выполнен (`e0f730b`):** 28 коротких граничных отрезков —
  несущие (alpha/A10 frontier: удаление меняет силуэт/открывает
  дыру); 2 внутренних — несущая offset-lift сварка
  owner-плоскостей 1<->3; необъяснённых рёбер НЕТ, удалений нет
  (корректный исход стопа). Повторяющиеся выемки по краю ленты на
  кривизне — артефакт production developable-пути (per-station
  MITER/SMOOTH policy), структурно поглощается R3 (RM1: геометрия
  по source-граням, без per-station вставок); RF12
  перепроверяется на приёмке R3.
- **RF13 Building: валидация по footprint + fold-берега (стопы
  R1.1):** выбранные seams (412/504/553 + boundary 476/598)
  компилируются и материализуются при наличии вне footprint грани
  с вырожденной fan-триангуляцией (face 277); валидная грань с
  коллинеарной fan-тройкой ВНУТРИ footprint материализуется
  (RV2); негатив: истинно вырожденная грань внутри footprint ->
  именованный fail. Итог маршрутизации: RAIL_PLANAR, НЕ
  RailUnsupported и НЕ Patch-fallback — building принимается в
  R1.1 (expected-fail до R3 остаётся только за настоящей
  кривизной, half_sphere). Boundary-rails на fold'ах работают
  общими берегами (RR8a): pieces атрибутированы по секторам,
  станции route общие, сварка угла по общим ключам.
- **RF14 Building: multi-spine вершина 231 (RP-режим):** стены
  копланарны -> секторные rails 417/472 и angular-русла НЕ
  создаются; in-plane ленты обеих стен клипятся линией boundary
  598 (скольжение), сварка угла по станционным ключам единого
  boundary-route 598 (RR8a); dam/cap/`CURVED_OWNER`/
  `BOUNDARY_AMBIGUOUS` отсутствуют; итог building: RAIL_PLANAR.
  (Прежние ожидания секторных rails/angular-русел перенесены в
  R3-фикстуры для несопланарных вееров.)
- **RF15 Building: spine-spine угол v153 (RP-режим):** веер
  копланарен -> внутренние рёбра не считаются, никакой секторной
  маршрутизации; угол обслуживается in-plane RM6a corner-paths +
  A10-клином; dam-route/`VIRTUAL_CAP_EMPTY`/`BOUNDARY_AMBIGUOUS`
  отсутствуют; итог building: RAIL_PLANAR. Синтетический негатив
  RM5a-деградации сохраняется как R3-фикстура (несопланарный
  веер).
- **RF16 Терминальные торцы (полевой тест 7, скрин со стрелками):**
  склон building/sagging: торцевые срезы ленты следуют
  fold/border-rails торцевых вершин (синие стрелки пользователя);
  внутренние rails без изменений; торец в середине плоской стены
  (нет fold-ребра) — перпендикулярный клип; негатив: >= 2
  fold-кандидатов без mark -> перпендикулярный клип, counted.
- **RF18 Терминальный снэп (RR9a):** конечная вершина spine с
  ДВУМЯ seam-рёбрами в patch стороны — одно почти
  перпендикулярно spine, второе косое: торец скользит вдоль
  почти-перпендикулярного; оба остаются принудительными границами
  (RR8); негатив 1: зеркально-симметричная пара (точная ничья) ->
  плотина, counted; с rail-mark на любом — мост; негатив 2:
  rail-mark на КОСОМ кандидате при существующем
  почти-перпендикулярном -> торец следует mark (разметка сильнее
  снэпа).
- **RF17 Нити между chains (RR10):** непланарная поверхность, две
  seam-цепочки, соединённые прямыми рёбрами (оба конца ребра — на
  разных цепочках): нити подсвечены как rails; на каждую нить —
  ОДИН route, читаемый обеими лентами (двойное чтение станций);
  R2: freeze вдоль нитей по станционной метрике двух чтений, S1
  при drag; вершина с >= 2 кандидатами, из которых ровно один —
  нить: нить выигрывает, плотины нет; негатив 1: >= 2
  нитей-кандидатов -> плотина, counted; негатив 2: та же
  конфигурация в копланарном регионе -> нить rail'ом не становится
  (RP), in-plane клип без изменений.
- **RF19 Terminal-bridge (RM9, полевые ракурсы пользователя):**
  арка `rounded_wall.001` и `sagging_wall` на production-пути:
  торцы ленты следуют примыкающим внешним pChain/fold-rails,
  прочитанным из rail-плана, на ДВУХ ширинах drag (видимое
  скольжение); неизменны faces, НЕ затронутые терминальным срезом
  (скоуп по RM9-fix; прежняя формулировка «интерьер бит-идентичен»
  была противоречива — признано); диагностическая строка
  routing-отчёта называет для каждого торца выбор плана (PCHAIN
  id / FOLD id / PERP) и материализующий backend; негатив: конец
  без кандидатов -> PERP, как раньше.
  **Негатив «нашлёпки» (RM9-fix):** в терминальной зоне НОЛЬ
  перекрывающихся faces; граница концевых faces ленты лежит НА
  терминальном rail; старая перпендикулярная граница при
  PCHAIN-гиде отсутствует; обязательный wireframe/edit-mode скрин
  терминальной зоны. Приёмка — полевые скрины пользователя с тех
  же ракурсов (синие стрелки) в edit mode.
- **RF18b Терминальный снэп на кривизне (RR9a-финал; активируется
  с R3):** конфигурация RF18 на непланарном patch — селектор
  идентичен (argmin |dot| в 3D, единый код с планарным); простые
  fold-рёбра при этом — rails по копланарности НЕЗАВИСИМО от
  снэпа; не-выбранные seam-кандидаты остаются границами-клипами.
- **RF10 Планарный L-поворот (in-plane 90 град.):** стабильная
  A10-семантика угла сохранена в rail-материализации (miter-стык
  как в production); differential пересдаётся осознанно.
  Corner-paths: ЧЕТЫРЕ односторонних в вершине поворота (по
  паре spine-рёбер на каждую из двух сторон); внешний сектор —
  клин между срезами, внутренний zero-сектор — concave-стык по
  A10; `SHARED_KEY_POSITION_DESYNC` невозможен по построению
  (ключи разносторонних path различны).
- **RF9 Reversed enumeration:** RF1-RF7 при обратном порядке
  рёбер — бит-идентичный результат.

## 7. Stop-условия TRANCHE R

- Потребность в ЛЮБОМ числовом tie-break — стоп (дизайн-вопрос
  ревьювера).
- Конфликт с bands-оракулом или admission-оракулом — стоп.
- Станционная метрика не разрешает конкуренцию (RC4) — стоп.
- Неоднозначность семантики merge на эмиссии — стоп.
- ТИХАЯ замена правил RR/RM/RC «более удобными» запрещена;
  ПРЕДЛОЖЕНИЕ изменений — приветствуется и обязательно к
  рассмотрению (§0f плана: голос исполнителя). Противоречивая
  или вредная директива — не для буквального исполнения, а для
  возражения с вариантами.

## 8. Связь с существующим планом

- G1.2 (imprint-пары) и C8.7 (V-клин) — ПОГЛОЩЕНЫ RM1/RM6.

  пользователя. Неподдержанный rail/chart component остаётся явным

- Атлас/GL/E-acceptance — пересматриваются ПОСЛЕ R: часть
  атласной сложности может стать ненужной (chart строится из
  rail-домена).
